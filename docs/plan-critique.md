Independent critique and revision decisions
==========================================

The requested critic agent reviewed the original plan, data preparation script and fixtures, the paper, and primary Ollama documentation. The original plan is preserved as `docs/plan-v1.md`; references below point to that version. The critic found no incorrect corpus counts, observed model-result leakage, or verified incompatibility in the example HTTP request. It found an incomplete execution and interpretation contract.

| Priority | Finding | Assessment and revision |
|---|---|---|
| Blocking | Batching and rescoring affect irreversible pruning but were underspecified (v1 lines 104–117). | Accepted. Define ordering, batch limits, pooled screening, a maximum twelve-item rescore prefix, overflow behavior, and one common ranker. |
| Blocking | Memory capacity does not establish laptop feasibility (v1 lines 62–64, 150). | Accepted. Page screening alone needs at least 26 requests/query and 6,734 over the evaluation. Require backend tests and a full-corpus design pilot against an explicit time budget. |
| Blocking | Failure scoring lacked a denominator (v1 line 154). | Accepted. In a completed run, failed queries have empty rankings, contribute no hit, retain failure status, and stay in the 259-query denominator. Also report the common successful-query intersection. Aborted runs are incomplete. |
| Important | Expansion after a small effect invites optional stopping; explored validation examples affect later full-validation claims (v1 lines 41, 52). | Accepted. Freeze one evaluation. Record fifteen explored validation dialogues; later full-validation scores are descriptive. |
| Important | Labels and reference answers share dictionaries with history (audit script lines 76–85). | Accepted as a construction risk, not an observed leak. Require separate input/label files, an allowlisted request builder, and sentinel checks on complete rendered requests. |
| Important | Baseline judging settings were ambiguous (v1 lines 129–134). | Accepted. Both judged systems use the same passage ranker, representations, context rules, and output limit. Report differing discovery pools, coverage, and compute; avoid a pure causal claim about hierarchy. |
| Important | Shared binary and multiple-choice comparisons test different mechanisms (v1 lines 138–140). | Accepted. Separate diagnostics; freeze pools and prompts. Reuse upstream traces for choice. Top-five permutation cannot change R@5 or R@10. |
| Important | The core differs materially from the paper's model and configuration (v1 lines 6, 101, 119). | Accepted. Call it a local adaptation. Defer routing, memory, dense retrieval, and generation. Jev execution remains outside the supported claim. |
| Minor | Many unadjusted intervals and balanced dialogue sampling could invite overgeneralization (v1 lines 142–146). | Accepted. Name one primary metric and contrast. Other intervals are exploratory; the micro average describes the selected mixture. |

I retained the full searchable corpus and frozen 259-query subset: reducing queries preserves the retrieval problem. I also retained Federal REAL ID as a display fixture, while recording all its fifteen exported validation dialogues as explored and disjoint from the evaluation. Its raw document ID has no eligible training examples, so the plan does not relabel them as training. Actual debugging uses the training design split.

The proposed rescoring remains a bounded heuristic. It does not prove calibration across contexts, and cannot recover candidates discarded during screening. The revised plan records coverage before and after that screening.

Independent parent-agent checks confirmed the request lower bound, median nine passages per merged page, maximum 63, a largest merged page of 23,769 words, and a largest three-page pool of 135 passages. The critic independently found that all title-plus-heading descriptions exceed the local 64 KiB request limit. These are corpus measurements, not inference benchmarks.

Compatibility sources: [System One API](https://docs.ollama.com/api/systemone), [decision guide](https://docs.ollama.com/capabilities/decision), and [Nimble model card](https://ollama.com/library/nimble). The installed server/model combination still needs a live gate. No model downloads, upgrades, or inference runs occurred in this revision.

The critic re-reviewed v2 and returned **pass with caveats**, confirming that the blocking findings were resolved and that the explored-dialogue registry matches the fixture with zero evaluation overlap. Its two remaining clarifications have been incorporated: local byte/token rejection follows the same split/prefix-reduction path as server size rejection; the two-hour budget is both a pilot planning threshold and a hard run deadline, while the infrastructure stop counter counts exhausted queries per method. Live backend compatibility, complete input fit, and runtime remain untested prerequisites.

It makes C-versus-D quality/latency the primary comparison, specifies Q8 variants and a common controller/input policy, adds the generative score adapter, and expands gates, scheduling, failure accounting, and reporting to all four options. The original A/B and B/C comparisons become secondary. This is a user-directed revision; the independent critic's recorded approval applies to v2, not a new review of v3. Frozen data manifests are unchanged.
