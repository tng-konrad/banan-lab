Local hierarchical decision retrieval with Ollama — revised plan v4
=================================================================

This revision incorporates a second independent critic's review of the four-option experiment. The first deliverable remains **a local adaptation of DecisionRAG testing hierarchical retrieval and the practical value of a decision model against an ordinary generative LLM**. It cannot establish the paper's Jev accuracy, specialized single-forward-pass execution, or hosted latency. Earlier plans are preserved in `docs/plan-v1.md`, `docs/plan-v2.md`, and `docs/plan-v3.md`. 1. Freeze a small core scope.

   The supplied paper, *Retriever-Free Retrieval: Navigating Documents with Decision Models* (Wan et al., arXiv:2610.35868v1), scores alternatives together while navigating a document hierarchy. Its MultiDoc2Dial configuration includes help-center routing, ten retained pages, two pages of retrieval memory, and twenty-way choice reranking. Its specialized model evaluates questions with a shared forward pass.

   The core local method is stateless **page → passage** navigation, three retained pages, candidate relevance judgments, and bounded shared rescoring. Run exactly these four required options:

   | Option | Candidate discovery | Judge | Purpose |
   |---|---|---|---|
   | A — BM25 | Lexical search over all passages | None | Lexical baseline |
   | B — BM25 + Nimble | BM25 top fifty passages | Nimble decision model | Added value of semantic judging over A |
   | C — Hierarchical decision retrieval | Page → passage navigation | Nimble at both stages | Navigation versus B using the same decision judge |
   | D — Hierarchical ordinary-LLM retrieval | The same page → passage controller | Qwen3.5-9B generating relevance scores at both stages | Same-controller generative-score baseline versus Nimble |

   The hoped-for accuracy ordering A < B < C is a testable hypothesis. There is no assumed accuracy ordering between C and D: the main question is their quality/latency tradeoff. D is a required comparator, not a fallback or optional extension. Defer multiple-choice reranking, help-center routing, memory, dense retrieval, answer generation, fine-tuning, and a chat UI.

   Paper reference results are R@1 47.4% and R@10 83.6% for Jev over 4,201 queries, versus 33.6% and 81.1% for dense retrieval plus Qwen3-Reranker-8B. Appendix D.1's shared-context result, 44.4% versus 36.7%, uses a different 297-turn design experiment. The 0.68-second median is a hosted API measurement on 48 timed queries. None is a direct target for the changed local method and subset.

4. Implement one exact ranking contract.

   Persist the full corpus with stable IDs and source-order indices. Page descriptions contain normalized titles and deduplicated headings; passage descriptions contain complete text plus title/heading path. B/C/D use identical passage descriptions, and C/D use identical page descriptions. Present candidates in corpus order even when a discoverer ranked them. Use short opaque aliases and record the mapping. Model queries contain only the last six role-tagged utterances. Earlier dataset replies are identical across methods; generated replies are not fed back. C and D run the same controller with a different judge adapter, so their actual page selections and later passage pools may diverge; neither receives the other's chosen branches.

   Initial design settings are `page_budget=3`, `binary_batch_max=16`, `rescore_prefix_max=12`, `output_k=10`, and `bm25_pool=50`. Guard request JSON at 48 KiB; this does not prove token fit. Use a common context ceiling no greater than either installed/validated limit and initially at most 8,192 tokens, reserving 512 tokens for D's compact output and applying the same resulting input ceiling to C. Gate A must establish backend-rendered token counts or a validated conservative fit bound for both wrappers. Pack B/C/D against the stricter admission result of both adapters, even though B uses Nimble only. Identical candidate lists must receive identical partitions and prefix admission decisions. Inability to establish complete nontruncated input blocks the confirmatory comparison, rather than becoming a footnote. Unexpected server size rejection after admission fails the query for B/C/D; it never changes one arm's evidence through an extra server-triggered fallback. Local deterministic splitting remains available before the call.

   `binary_batches` is the shared interface name for both adapters. It greedily packs candidates in source order, respecting sixteen relevance questions and the common input limits. Each question sees every candidate of its batch. Nimble answers each via `noul`; Qwen generates a compact score for each of the same questions. A common local byte/token admission rejection splits the batch into contiguous halves; a singleton rejection fails the query. Unexpected server size rejection after admission is a query failure in B/C/D alike. Nothing is truncated, summarized, dropped, or assigned a fabricated value. Other errors follow the retry policy. Log actual batches: changing context limits changes this method.

   `rank_pool` pools candidate scores and sorts by score descending, then stable corpus ID. This is approximate cross-context screening, not calibrated global comparison. Take the first twelve candidates and rescore the largest leading prefix that fits one common context, presented in source order. On common local size rejection, remove its lowest-ranked candidate until at least two fit; apply the same stricter-of-both-adapters predicate for B/C/D. Unexpected server rejection after admission fails the query for all three. Reorder this prefix by its new scores and append the untouched coarse-ranked remainder. If fewer than two fit, keep the coarse ranking and record skipped rescoring. This declared fallback removes nothing from the discovered pool. Other rescore errors fail the query. Log shortlist gold coverage, prefix length, and skip rate. Different model rankings may yield different prefix contents, but identical candidate lists obey identical rules.

   ```python
   def rank_pool(history, items, n, judge):
       coarse = judge.binary_batches(history[-6:], source_order(items), max_items=16)
       ordered = stable_score_order(coarse)
       prefix, refined = judge.rescore_fitting_prefix(
           history[-6:], ordered[:12], presentation_order="source", min_items=2)
       if refined is not None:
           ordered = stable_score_order(refined) + ordered[len(prefix):]
       return ordered[:n]

   def navigate(history, corpus, judge):
       pages = rank_pool(history, corpus.pages, n=3, judge=judge)
       return rank_pool(history, corpus.passages(pages), n=10, judge=judge)

   def bm25_then_judge(history, corpus, bm25, judge):
       ids = bm25.top_k(history[-6:], k=50)
       return rank_pool(history, corpus.passages_by_id(ids), n=10, judge=judge)

   # The four options; navigate and rank_pool are unchanged between C and D.
   A = bm25.top_k(history[-6:], k=10)
   B = bm25_then_judge(history, corpus, bm25, nimble_judge)
   C = navigate(history, corpus, nimble_judge)
   D = navigate(history, corpus, qwen_generative_judge)
   ```

   The helper returns the actual leading prefix and its scores, or an empty prefix/`None` when fewer than two fit. There is no hidden choice, routing, retrieval memory, or answer-generation stage. D's score-token generation is explicit in its adapter. Rescoring cannot recover candidates discarded by screening. Never claim all selected passages shared a context when only batches or a shortlist did.

   Nimble requests use `state={conversation, candidates}` and `questions={alias: {type: "noul", instructions: ...}}`; scores come from `answers[alias].noul`. Qwen receives the same conversation, candidates, aliases, and question wording through `/api/generate` with [structured outputs](https://docs.ollama.com/capabilities/structured-outputs). Its schema is an object containing `scores`, with every alias required, numeric values in [0,1], and additional properties forbidden. For example: `{"scores":{"c001":0.93,"c002":0.12}}`. These generated relevance scores are ranking heuristics, not measured token probabilities or calibrated confidence; use only within-model rankings, never subtract a Nimble probability from a Qwen score. The different scoring interface is part of the compared systems.

   Qwen's initial settings are `temperature=0`, `seed=42`, `num_predict=512`, `stream=false`, and the metadata-verified no-thinking setting. Use a concise anchored rubric: 0 = no useful evidence; 0.5 = related but insufficient alone; 1 = directly useful evidence for the next reply. Permit intermediate relevance values and initially request at most three decimal places. The rubric, precision, prompt, and output limit are design settings frozen before evaluation; generated scores are not confidence probabilities. Log output-token count, tied-score fraction, number of distinct scores, and all-equal batches. Do not inject jitter or change precision after seeing evaluation ties. A small design-only compact-ID ranking check can assess whether the numeric interface is a competent baseline; it is not a fifth required option. Selecting a different D interface requires a new frozen protocol before evaluation.

   Request scores only, without explanations or tools. A truncated output, unrequested thinking output, invalid JSON, missing/extra alias, or invalid score is an explicit failure. Output-limit tuning happens only in the pilot and changes the common input reserve. Nimble may process questions separately while Qwen generates several tokens; record all usage and wall time. Fix page/passage questions across the adapters, with only API-specific framing. Treat corpus content as evidence, not instructions; never serialize labeled records. The [generation API](https://docs.ollama.com/api/generate) documents model-specific thinking controls. D is specifically a generative-score baseline with the same controller: paper Section 6.3 instead generates kept candidate IDs and rankings. C/D outcomes therefore include numeric scoring, ties, and serialization behavior; they do not reproduce that exact generative baseline or isolate training from inference mode.

   A small package needs `data.py`, `judge.py` (Nimble and ordinary-LLM adapters), `retrieve.py`, `evaluate.py`, one CLI, and one explanatory notebook. Suggested dependencies: `httpx`, `numpy`, a pinned BM25 implementation, and `pytest`. Freeze BM25 normalization, stemming/stopwords, parameters, and six-turn serialization. All passage methods see the same title/heading/text content. Tests cover label mapping, ordering/ties, prefix replacement without duplicate IDs, splits without lost candidates, rendered-input isolation, both score parsers, identical B/C/D admission/error rules, the common controller with no branch leakage, and the primary verdict refusing a success-selected timing win. Persisting the runnable corpus and separated input/label files remains implementation work.

5. Freeze the four-option comparisons and define failures.

   Run A/B/C/D over the same 259 queries. A-versus-B tests adding Nimble judging to BM25; B-versus-C tests navigation versus reranking BM25's discovered pool with the same Nimble model. These remain **system-level quality/cost comparisons**, since discovery pools and compute differ. C-versus-D is the primary comparison for decision-model value: same hierarchy, controller, candidate representations, questions, page/output budgets, admission policy, and hardware, with different judge adapters. Actual selected branches may differ and are part of the end-to-end outcome. There is no required strict A < B < C ordering and no assumed winner between C and D.

   Primary contrast: **C (Nimble navigation) versus D (ordinary-LLM navigation), measured jointly on operational R@1 and latency**. The proposed frozen quality margin is two percentage points (`delta=0.02` absolute R@1), never relaxed after results. Let `quality_difference=R@1(C)-R@1(D)`. A confirmatory local efficiency win requires: the full four-option run is complete; input-fit and warm-residency controls hold; **C and D both return valid rankings for all 259 queries**; the paired 95% lower bound for quality difference is above `-delta`; and the paired 95% upper bound for the ratio of median full-query times `C/D` is below one. Time all 259 C/D queries, including retries and protocol admission work. With full C/D validity there is no success-selected latency cohort. A failure in either arm makes the primary efficiency verdict inconclusive, even if conditional latency looks favorable. Still report operational quality, all-attempt time-to-result-or-failure, and common-success timing descriptively, each with its denominator. Do not repair the primary result by dropping failed cases.

   A nonsignificant quality difference is not equivalence. If quality improves at greater time cost, report that tradeoff. With forty dialogue clusters a two-point margin may be difficult to resolve. Before freezing, use paired disagreements observed on training data, when available, to forecast interval precision; label a ten-query forecast highly uncertain and do not treat tuning data as an unbiased power guarantee. This forecast cannot justify later changes to the held-out sample or quality margin. A-versus-B and B-versus-C remain secondary descriptive comparisons.

   In a completed run, all four options attempt all 259 queries. Exhausted transport/schema/context or generation failures have empty rankings and contribute no hit to operational R@1/5/10. Preserve failure categories; never fabricate zero candidate scores. Valid empty results and invalid calls have different statuses. Additionally report quality on the intersection of successful queries for each compared pair, plus the all-four common-success intersection, with every denominator shown. Operational quality keeps all 259 queries even when some fail. An aborted run is incomplete and has no confirmatory verdict.

No retry or hidden repair for malformed schemas, invalid/truncated scores, unsupported APIs, or unexpected server size rejection after admission. Shared local size admission and prefix reduction are separate actions. Count all attempts and time. Run a paired C/D sweep first, in manifest query order with C/D order seeded within each query; only after that sweep run A/B on the same fixed queries, with seeded A/B order. A/B timing occurs in a later session phase and is secondary, not a precisely simultaneous B/C speed control.

   Keep both models loaded using an explicit retention setting supported by their endpoints (initially `keep_alive=-1`), warm them with training-only probes before the C/D sweep, and verify residency through `ollama ps` or equivalent metadata. Record load/queue time, cache-hit/prompt-evaluation counters where exposed, and timestamps. 6. Keep mechanism diagnostics separate.

   After the core, use fifty hash-selected training-design queries for an exploratory **competitor-context diagnostic**. Each fixed pool contains gold plus nine BM25 hard negatives, excluding exact normalized gold-text copies. Freeze pool, shuffled order, aliases, descriptions, and question wording. Compare the same binary question over its target alone versus the complete ten-candidate state. Send one question/request in both arms so the other question schemas do not change the comparison. Rank the same pool. Gold inclusion makes this an oracle diagnostic, never end-to-end retrieval. Establish input fit before scoring; if pools cannot fit under one frozen policy, report unsupported instead of dropping long cases. Findings on design data remain exploratory.

   A separate **choice diagnostic** compares one choice question over those pools with shared binary ranking. It changes decision type; its whole effect is not attributable to competitor context. A pipeline choice ablation reuses saved upstream page/passage traces and permutes only the top five returned candidates. Its target is R@1: such a permutation cannot change R@5 or R@10. A five-item context overflow fails that ablation query under the same scoring contract, rather than changing the pool after an outcome. Check position sensitivity with a small design-only permutation exercise before freezing order.

   Paper Appendix D.1's separate-per-page versus shared-across-pages experiment is distinct.
